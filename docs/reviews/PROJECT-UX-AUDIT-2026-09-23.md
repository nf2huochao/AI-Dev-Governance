# AI 开发治理局 V0.1 整体项目与 Skill 体验审查报告

日期：2026-09-23  
审查分支：codex/skill-ux-review  
审查基线：f1a8cb0327b96c60cc2467af2b75b82b12a9c8cf  
结论：已完成一轮以首次安装、Team-First Bootstrap、身份绑定、恢复、证据边界和普通用户体验为中心的修复。确定性回归通过；真实 Codex 多对话送达/唤醒和实际 MCP 连接仍需独立人工实测，不能据此宣布平台能力已解决。

## 1. 总体判断

项目的四角色职责、Single Writer、独立审查和事件驱动接力方向合理。主要问题不在核心理念，而在“规则写得很严，首次使用却仍让普通用户承担内部工程操作”，以及部分脚本把结构一致性误当成平台真实性。此次保持四角色模型不变，集中修复入口、安装、初始化、恢复、证据和测试基础设施。

## 2. 已确认并修复的问题

### 严重：人工文件可能形成自我授权

旧启动检查允许人工 JSON 中的状态和哈希组合成为启动依据。文件内容一致只能证明文件未变，不能证明谁批准、消息是否真实送达或 MCP 是否真的读取工程。

修复：

- 启动检查始终明确返回 MANUAL_REQUIRED、platform_attestation=false、authorization_authenticated=false、may_start_mission=false。
- 即使旧授权回执字段和所有哈希完全匹配，也只标记为结构匹配、未经认证。
- 新增事件日志哈希，证据变化会令旧回执失效。
- 无 JSON 输出模式时使用非零结果，防止旧自动调用者把脚本完成误认为可发布 Mission。
- README 和首次使用说明不再把结构测试写成真实平台通过。

### 严重：正式角色模板与角色创建守卫互相冲突

初始化模板把司策令和执造者目标记录为 NOT_CREATED，旧守卫却要求另一种待创建值，导致真实首次初始化后无法合法创建两个角色。解析器还会忽略某些畸形或重复角色行。

修复：

- 创建守卫接受模板定义的唯一合法待创建状态。
- 严格要求项目身份、Bootstrap 状态、固定角色列数和角色唯一性。
- BOUND 身份和通信目标不得使用占位符、显示名或与其他角色重复。
- Core Architect 始终禁止创建，必须复用原始对话。
- 复制到其他目录的旧角色表因工作区身份不一致而停止，不再静默复用。

### 高：普通用户承担线程号、哈希、脚本和模板工作

旧指南要求普通用户执行长命令、填写项目 ID、线程 ID、通信句柄和授权 JSON，首次体验接近开发者调试手册。

修复：

- SKILL.md 改为精简的 Agent 入口，内部执行细节移入 Bootstrap 执行规程。
- 普通用户指南只保留六个真实动作：安装、确认工作区/名称、等待团队通信核验、批准摘要、完成平台授权、继续或恢复。
- Codex 负责生成项目身份、保存摘要、运行检查和维护记录。
- 用户无需填写 PASS、线程号、哈希或授权 JSON。
- 项目规划提示词带入已知上下文，不重复询问已有信息，每次只问一个会改变范围或验收的问题。
- 新增只读进度检查，返回当前阶段、下一步和诊断，不写文件、不创建角色、不放行开发。

### 高：重复调用或中断恢复可能重复建角色

旧入口倾向把每次调用都当成原始天枢核启动，容易造成身份混乱和重复角色。

修复：

- 入口先区分新项目、已有治理项目、已绑定司策令/执造者和 Skill 产品开发场景。
- 已有项目先读取角色表和状态，复用身份、角色显示名和批准摘要。
- Recovery 必须追溯司策令和执造者的历史真实创建记录；不能靠手写当前 BOUND 状态绕过。
- 当前对话身份无法可靠取得时停在 BINDING_BLOCKED / CAPABILITY GAP，不创建替代天枢核。
- 创建结果不确定时只能核实一次，不盲目重试或轮询。

### 高：安装包可能夹带本地开发文件

旧安装器递归复制 scripts 等目录，本地未跟踪配置或临时文件可能被一并安装；同名 Skill 使用引号时也可能漏检。

修复：

- 新增 runtime-files.json 明确运行时白名单，只复制清单中的单个文件。
- 拒绝绝对路径、路径穿越、重复项、符号链接及 tests/.git/.test-artifacts。
- 同名 Skill 检查兼容单双引号 frontmatter，已有安装时停止，不覆盖。
- 安装使用目标卷上的隔离临时目录，逐文件 SHA-256 核对后原子落盘。
- 生成 INSTALLATION.json，记录包版本、源码提交（可取时）、dirty 状态和文件哈希。
- 明确“安装复制成功”不等于 Codex 自动发现或真实通信通过。
- 新增 agents/openai.yaml，提供清晰名称、简介和默认首次调用提示。

### 中：接力日志允许已完成 TASK 被静默重开

旧检查器没有阻止 PASS 后再次使用相同 TASK_ID 或 EXECUTION_ID；控制事件也缺少项目和证据字段检查。

修复：

- 同一日志项目身份不可变化。
- PASS 后相同 TASK_ID 不可再次 DISPATCH。
- 新任务不可复用旧 EXECUTION_ID。
- 控制事件要求 execution_id、role_id、thread_id 和 evidence。
- JSONL 每行必须是真实 JSON 对象，不能用数组或简单值。
- BLOCKED/ESCALATE 的既有恢复约束保持兼容。

### 中：测试可能漏跑或跨 PowerShell 版本失真

旧 CI 在同一进程逐个执行脚本，某个脚本 exit 0 可提前结束整个测试集；部分测试又固定调用 Windows PowerShell，使 PowerShell 7 矩阵没有真正测试同一运行时。

修复：

- 新增独立测试运行器，每个测试文件在独立、与当前矩阵一致的 PowerShell 进程中运行。
- CI 使用 Windows PowerShell 5.1 与 PowerShell 7 两套矩阵。
- 对包含中文的 PowerShell 文件使用兼容 Windows PowerShell 5.1 的 UTF-8 BOM。
- 补充 11 项真实模板/安装包/恢复用户路径回归，而非仅检索文档关键词。
- 双版本测试不可并行共享临时目录；本次最终验证采用顺序运行，避免测试互相删除文件。

## 3. Skill 体验变化

首次调用会先判断“这是新建治理团队、恢复已有项目，还是在开发 Skill 本身”，不再无条件把当前对话改成天枢核。新用户一次确认工作区和名称后，Codex 完成安全初始化；任何身份、通信或平台能力缺口都会给出当前状态和一个明确下一步，不要求用户操作内部文件。中断后只需在原天枢核说“从已有记录恢复，不要重复创建角色”。

MCP 指南也已收紧：不再假设所有 Plus 用户都有统一入口，不再以路径字符串一致冒充实际连接成功；必须完成真实只读读取才能作为启动证据。

## 4. 回归结果

- Windows PowerShell 5.1：17/17 测试文件通过。
- PowerShell 7.6.5：17/17 测试文件通过。
- 新增用户路径回归：11/11 通过。
- Git diff 检查：通过，无空白错误。
- 敏感模式扫描：未发现疑似真实 API Key、Token、Cookie、密码或 Session。
- 隔离安装：通过；未列入白名单的本地配置没有进入安装包。

这些结果只证明本地确定性行为和文档/脚本契约，不能替代真实 Codex UI 自动发现、三个独立对话的消息送达与唤醒、或 ChatGPT MCP 实际连接测试。

## 5. 仍然存在的真实限制

1. 当前工具没有可靠的“取得当前调用对话 threadId”专用接口。不能从标题、最近时间或工作区猜测，因此首次真实通信可能仍停在 CAPABILITY GAP。
2. 创建工具在准备阶段可能只返回 clientThreadId；它不能作为消息工具所需的 threadId。
3. 发送工具成功只证明请求已提交，不证明接收方执行或发送方被回唤。
4. 当前本地脚本不能认证平台原始通信记录，也不能认证一份 JSON 是否真的由 Human Governor 批准。
5. MCP 的入口、权限和可读范围依账号与客户端实际能力而定，尚未证明对所有 Plus 用户通用。
6. 公开 GitHub 标签 v0.1.0-beta.1 仍是旧公开版本；本报告对应本地候选修复，尚未推送或发布。

## 6. 发布前建议

在隔离新项目中完成一次真实最小验收：Codex 自动发现 Skill；原对话身份可核实；只创建一个司策令和一个执造者；两组 HELLO/ACK 有双向实际执行和回唤证据；用户批准摘要可定位；外参师通过实际连接读取正确项目的一份非敏感文件。全部成立后再合并并准备新的 Beta 版本，不要覆盖旧标签。
