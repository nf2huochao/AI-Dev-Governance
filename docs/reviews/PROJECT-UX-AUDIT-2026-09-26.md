# AI Dev Governance 项目与 Skill 体验审查

日期：2026-09-26。基线：公开 v0.1.1，提交 `57a041894bacef417a9413255d2c0cb0a6806db1`。
修复分支：`codex/ux-audit-20260926`。本报告在 v0.1.2 发布前撰写；当时修复尚未进入公开版本。

## 整体判断

四角色、事件驱动接力、单一业务代码写入者与独立审查的分工可以保留。本轮发现的问题主要集中在“再次调用”和“中断恢复”：已有状态没有被用于决定下一步，损坏记录又可能被初始化掩盖。结果是用户反复规划、重复确认，甚至误以为缺失的历史已经恢复。

按 Skill 编写指南，修复聚焦能改变实际行为的规则和脚本：复用原摘要、原角色和当前任务，给出具体恢复动作，减少重复流程。未重写四角色架构。

本轮检查了入口与发现信息、安装白名单、初始化、角色绑定与创建检查、基础通信校验、正式启动检查、进度恢复、接力校验、Watchdog 和中英文用户资料。修复范围由实际复现与文本冲突决定，不代表穷尽所有平台缺陷或完成陌生用户验收。

## 已修复问题

| 编号 | 实际问题与影响 | 修复与验证 |
|---|---|---|
| UX-01 | 已保存获批摘要后，进度仍要求重新规划和批准摘要 | 进入 VERIFY_STARTUP，定位已有批准与缺失证据；失败样例转为通过 |
| UX-02 | BOOTSTRAP_STATE=COMPLETE 且已有 HANDOFF，进度仍回到初始化 | 显示 RESUME_RELAY、当前 Mission/TASK/状态；不自动发任务；失败样例转为通过 |
| UX-03 | 再运行初始化时，输出始终写 ACTIVE，与已保存 COMPLETE 冲突 | 恢复输出使用注册表原状态；失败样例转为通过 |
| UX-04 | 角色表丢失但日志仍存在时，初始化生成新的项目身份 | 写入前报 ROLE_MAP_RECOVERY_REQUIRED，不改动已有资料；失败样例转为通过 |
| UX-05 | 注册表存在但事件日志丢失时，初始化创建空日志 | 写入前报 RELAY_HISTORY_RECOVERY_REQUIRED，要求恢复原历史；失败样例转为通过 |
| UX-06 | 通用治理检查没有要求角色表，角色身份全部丢失仍 PASS | 增加角色表、项目路径与四角色记录完整性检查；失败样例转为通过 |
| UX-07 | 角色初始化说明要求直接 ACK；创建工具可立即启动角色，此时 HELLO 或 Executor 绑定可能尚未存在 | Core 等两个目标登记后开始 HELLO；Planner/Executor 只回复真实 HELLO，恢复使用对应 RECOVERY 消息。该项为指令冲突修正，尚待真实平台行为验证 |

新增回归中，6 个用例在修复前失败；另有 2 个保护性场景，验证不完整的新恢复握手不能复用旧成功，以及 COMPLETE 字段不能掩盖摘要缺失。它们全部是明确标注的本地样例，不是实际通信证据。

## 关键边界

- `may_start_mission` 始终为 false。显示“可定位当前接力”不等于认证授权；调用方仍须核对真实平台记录与已有批准。
- 不重建角色、不覆盖用户项目、不清空日志；损坏记录从 Git、备份或可核实原始记录恢复。
- 旧项目保存的角色规则不会被安装或初始化悄悄覆盖。现有团队应在当前任务结束后比对并加载新版规则，保持原线程身份。
- MCP 真实连接仍为既定启动前提。本轮没有把文件比较或手工 PASS 当成连接成功。

## 尚存限制

可靠的当前对话身份、消息回唤、账号可用的 MCP 入口仍依赖实际宿主能力。当前工具不能独立认证这些事实，本地脚本不应尝试用更多可填写字段替代证明。

四角色建立和外参师连接对新用户仍有操作成本。本轮减少已完成步骤的重复要求，但没有改变已批准的 Team-First 顺序或取消独立审查前提。

本报告记录当时的发布状态。修复后续是否已发布以 GitHub 的 v0.1.2 发行页为准。
