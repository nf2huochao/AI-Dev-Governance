# AI 开发治理局：首次使用指南

你只需确认项目位置、接受或修改四角色名称、批准项目摘要，并完成平台要求的授权。
保存文件、检查记录和执行内部命令由 Codex 负责。不要把 Skill 开发仓库当成新项目。

GitHub 的 `v0.1.2` 包含本次改进；历史版本不包含这些修复。
首次使用、真实多对话通信和 MCP 仍须实测，不能用脚本通过替代。

## 1. 安装并找到 Skill

在 Codex 对话中发送：

> 请从 https://github.com/nf2huochao/AI-Dev-Governance 的 v0.1.2 版本安装 ai-dev-governance 当前公开测试版；先检查已有同名安装，发现旧版时先说明备份更新方案，不要覆盖。

Codex 应先检查来源和安装清单；安装成功后会给出实际位置和版本。默认位于当前用户的 .agents/skills/ai-dev-governance。

安装后新建 Codex 对话，输入 $ai-dev-governance 或从 Skill 选择器选择“AI 开发治理局”。
找不到时重新启动 Codex，再试一次。仍找不到，把提示或脱敏截图交给安装对话检查；
不要反复安装同名副本，也不要自己修改系统配置。
旧版备份应放在 Skill 扫描目录之外，留在扫描目录内的改名副本仍可能被识别。

## 2. 确认工作区和名称

在 Codex 选择你准备用于新软件的项目文件夹，新建对话，发送：

> $ai-dev-governance 请帮我建立这个项目的治理团队。先确认工作区，角色名称使用默认值。

成功时应先看到工作区确认，以及“当前对话就是唯一的天枢核，只另外建立司策令和执造者”。
目录非空时，Codex 应说明已有内容，不清空文件。你可以一次修改四个显示名。
如果它开始直接写业务代码、让你填写线程号，或要再建一个天枢核，请让它停止并核查当前绑定。

## 3. 等待团队与基础通信核验

仍在最初 Codex 天枢核对话中操作。已批准范围内的角色建立和通信检查由 Codex 完成；
只需处理平台真正出现的权限提示，不需要每一步再回复“继续”。

成功应看到另外两个独立 Codex 对话，以及有真实回传依据的基础通信结果，而不只是“消息已发送”。
暂时没有后续消息时，回原天枢核说“请核实当前进度，复用已建立的角色”。不要重新创建团队。
如果显示 MANUAL_REQUIRED（需要实测核验）或 CAPABILITY GAP（平台能力不足），应得到具体原因和一个恢复动作。
拿不到可靠身份或无法唤醒时，不会继续正式开发，也不能把单对话模拟当作真实团队。

## 4. 到 ChatGPT 规划，批准后复制回来

通信核验通过后，天枢核会给你一段已带项目背景的完整提示词。
在 ChatGPT 新建外参师对话，将它粘贴进去，讨论项目目标、第一版范围和验收标准。

ChatGPT 应给出《项目启动摘要》初稿。满意后明确回复“我批准这份项目启动摘要”，
再把完整获批摘要复制一次回最初 Codex 天枢核。不需要手改 Markdown 或自行保存资料文件。
如果摘要不符合需求，留在外参师对话修订，不批准；天枢核不能自行替你批准。

## 5. 核实外参师工程访问

按照天枢核针对你当前平台实际提供的[连接指导](MCP-EXTERNAL-ADVISOR-SETUP.zh-CN.md)，
在 ChatGPT 完成必要授权。不要把密钥、Cookie、客户数据或敏感代码粘贴出来。

成功应看到外参师通过实际只读连接，确认同一项目并读取一份允许读取的文件。
仅显示路径一致不算连接成功。没有可用入口或读不到文件时，报告实际提示，停在需要核验状态；
不要另行购买服务或扩大授权来试错，除非你明确决定。

## 6. 启动及下次继续

天枢核会说明已核实的项目、摘要、团队通信和 MCP 状态，再依据你的真实批准启动开发。
你不需要填写 PASS、授权 JSON 或计算哈希。已有批准可定位时不必反复批准同一事项。

正式运行后，司策令派发、执造者执行并交接、司策令验收；普通接力不用你复制消息。
对话中断时，在原天枢核说“继续这个项目，从已有记录恢复，不要重复创建角色”。
如需回到司策令或执造者处理所属任务，它们保持原角色，不因再次调用 Skill 变成天枢核。

遇到问题见[恢复指南](FAILURE-RECOVERY.zh-CN.md)。反馈时只提交脱敏错误和复现步骤，
不要公开凭据、私人项目源码或整份敏感日志。
